# pwa

## 前提

PWA に単一の仕様はない。Web App Manifest と Service Workers の組み合わせ。

- Manifest https://www.w3.org/TR/appmanifest/
- Service Workers https://www.w3.org/TR/service-workers/
- 実装ガイド https://developer.mozilla.org/ja/docs/Web/Progressive_web_apps

PWA 化を「manifest を置いて Service Worker で全部キャッシュすること」と捉えると失敗する。品質を決めるのはインストール可否ではなく、オフライン・更新・認証・同期・端末差分をまたいでユーザーの作業が失われないこと。

## 手順

1. 重要タスクを1つ定義する。ユーザーがオフライン・低速回線・アプリ再起動・新バージョン公開をまたいで完遂すべき操作は何か。ここを決めずに実装を始めない。
2. Service Worker も JavaScript もない状態で、主要情報と主要導線が機能することを確認する。PWA はその上の段階的強化。
3. Manifest でアプリ識別子、起動先、範囲、見え方を固める。
4. Service Worker で画面・静的素材・API データを役割別にキャッシュする。
5. オフライン時の読み取り、入力、送信待ち、同期失敗を設計する。
6. Push、共有、ファイル連携、ショートカットは利用価値が明確なものだけ足す。
7. iOS Safari、Android Chrome、デスクトップ Chrome/Edge、未インストールの通常ブラウザ表示の全経路で確認する。

PWA はインストール済みアプリとしても通常の Web としても使われる。特定 API の有無で基本機能を壊さない。機能検出で分岐する。

## 重要タスクの切り分け

オフラインで保証するものと、オンライン必須のものを先に分ける。

- コンテンツ — 既読記事、保存済み一覧、下書きはオフライン。最新取得とコメント投稿はオンライン。
- EC — 商品閲覧、カート確認、後で買うリストはオフライン。決済、在庫確定、価格確認はオンライン。
- 業務 SaaS — 参照済みデータ、入力・編集、下書きはオフライン。競合解決、権限判定、正式保存はオンライン。
- 予約・注文 — 過去分の確認と入力途中の保持はオフライン。空席確認、確定、決済はオンライン。

## Manifest

```json
{
  "id": "/",
  "name": "Example Workspace",
  "short_name": "Workspace",
  "lang": "ja",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "display_override": ["window-controls-overlay", "standalone"],
  "theme_color": "#0b57d0",
  "background_color": "#ffffff",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any" },
    { "src": "/icons/icon-512-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ],
  "shortcuts": [
    { "name": "新規作成", "url": "/new",
      "icons": [{ "src": "/icons/new-96.png", "sizes": "96x96", "type": "image/png" }] }
  ]
}
```

- id を初期から固定する。後から変えるとブラウザが別アプリとして扱う。URL 構成や start_url を変えてもアプリの同一性を保つため。同一オリジンであること。
- scope を省略しない。省略すると start_url のパスがフォールバックになり、意図しない範囲に狭まる。狭いとアプリ内リンクで通常タブへ飛び、没入感が壊れる。全体なら "/"、サブパスだけなら "/app/"。
- start_url に個人識別子を入れない。userId、メールアドレス、会員番号、トークンは不可。追跡識別子になる。?source=pwa 程度の起動元計測は可。
- アイコンは 192、512、maskable 用 512 以上を用意する。maskable は丸型マスクで端が切れるため、中心に余白を持たせた別デザインにする。単純な縮小で済ませない。
- background_color は本体 CSS 読み込み前の起動画面の色。初期画面の実際の背景と揃えないと起動時に白くフラッシュする。theme_color は OS/ブラウザ UI との調和用。
- shortcuts は重要度順に少数。OS やブラウザが表示数を制限し、表示方法も保証されない。通常のアプリ内導線を必ず残す。

favicon や apple-touch-icon を含むアイコン一式は favicon スキルを参照。

## キャッシュ戦略

全て Cache First にしない。古い HTML と新しい JS と古い API レスポンスの組み合わせが事故の中心。リソースごとに分ける。

- ビルド済み JS/CSS/フォント — Cache First。ハッシュ付きファイル名にする。内容が変われば URL が変わるので安全。
- アプリシェル — Precache。起動に必要な最小画面をオフラインでも出す。
- HTML ナビゲーション — Network First。失敗時にオフラインページかアプリシェル。古い HTML と新しい JS の不整合を防ぐ。
- ユーザー固有 API — Network First。Stale-While-Revalidate は慎重に。鮮度と権限と個人情報を優先する。
- 画像・公開コンテンツ — Stale-While-Revalidate、または Cache First に有効期限。
- POST や更新操作 — 即時キャッシュしない。ローカルの永続キューへ。二重送信、競合、古い認可情報の使用を防ぐ。

認証済みレスポンスを雑に共有キャッシュへ入れない。ログアウト後に同じ端末の別ユーザーへ見える、権限変更後も古い機密データが残る、といった事故になる。端末に個人データを残すなら、何を保存し、いつ削除し、ログアウト時にどう消すかを明示的に決める。

## Service Worker のライフサイクル

常駐しない。イベント時に起動し、処理後に停止される。バックグラウンドで動き続ける Node.js のようなものとして設計しない。

- グローバル変数に重要な状態を置かない。
- 途中状態、送信キュー、同期対象は IndexedDB などに永続化する。
- fetch、push、sync の処理は毎回ゼロから復元できるようにする。
- イベント内の非同期処理は event.waitUntil() で寿命を延ばす。
- 長時間 CPU を占有する処理や無限ループを作らない。
- Service Worker 起動待ちがナビゲーションを遅らせるなら Navigation Preload を検討する。

## 更新フロー

新しい Service Worker は既存タブが開いている間 waiting で待つ。放置するとデプロイ済みなのに一部ユーザーだけ古い版という状態が続く。

1. 新しい Worker を検出する。
2. 更新があることをユーザーに提示する。
3. 承認されたら SKIP_WAITING メッセージを送る。
4. controllerchange を受けて1回だけ再読み込みする。
5. フォーム編集中、未送信データがある、決済フロー中は即時更新を避ける。

無条件の skipWaiting() と clients.claim() は、旧 JS が開いたまま新キャッシュへ切り替わりデプロイ中の互換性を壊す。アプリシェルをハッシュ付きアセットで構成し、旧版と新版が一時的に共存しても成立するリリース設計にする。

## オフラインと同期

オフラインはエラー画面ではなく継続可能性。最低限、ブラウザ標準のネットワークエラーではなく自サービスの文脈を持つ画面を出す。その先は、最後に取得したデータの閲覧、入力下書きの保持、送信待ちキュー、復帰時の同期まで含める。

復帰時の自動送信に注意する。注文、決済、予約確定、削除、承認など副作用の大きい操作は勝手に実行せず、再確認を求めるか、サーバー側で冪等性キーを検証する。

オフライン編集を扱うならサーバー API 側にも必要なものがある。

- 作成・送信系リクエストに冪等性キーを付ける。
- 更新対象にバージョン番号、ETag、updatedAt を持たせる。
- 古い編集が最新データを上書きしない楽観ロック。
- 競合時の方針を決める。サーバー優先、端末優先、フィールド単位マージ、ユーザーに選ばせる。
- 同期失敗を黙殺しない。失敗理由、再試行、破棄をユーザーが判断できるようにする。

PC とスマートフォンで同じデータをオフライン編集した場合、最後に同期した端末が全面上書きではデータを失う。最低でも競合を検知して差分と選択肢を見せる。

## インストール導線

初回訪問でインストールモーダルを出さない。価値を理解した後に促す。

- 記事やデータを保存した直後。
- 2回以上訪問し特定タスクを完了した後。
- 通知の価値が明確な機能を有効化した後。
- 電波が不安定な環境で使っている時。

「アプリを入れる」ではなく、そのサービス固有の便益で伝える。「移動中でも下書きを続けられる」「ワンタップで今日の予約を開ける」。

インストール済みでは、トップページの宣伝ではなく次に行う作業に着地させる。今日のタスク、前回開いた案件、続きから読む、カートと再注文など。

## URL を捨てない

PWA でも各コンテンツに固有 URL を持たせる。ブックマーク、共有、再訪、検索、通知からの遷移、ディープリンクのすべてに効く。SPA でも URL を変えずに画面だけ差し替えない。戻る操作、再読み込み、別端末への共有、検索での発見性が壊れる。

## 通知

即時性より期待値を優先する。不要な通知は許可拒否、アンインストール、信頼低下に直結する。

- OS の許可ダイアログの前に、独自画面で価値を説明する。
- ユーザーが選んだ種類と頻度に限定する。
- 全通知にディープリンクを付け、遷移先で目的が完結するようにする。
- 既読・処理済みを再通知しない。
- 種類別にいつでも停止できる設定を置く。
- 緊急でないものはバッチ化し、時間帯とタイムゾーンに配慮する。

## アクセシビリティ

タッチだけでなくキーボード、マウス、ペン、スクリーンリーダー、ズーム、横画面に対応する。

- ネイティブの button、a、input、form を優先する。
- フォーカス順序、フォーカス表示、モーダルのフォーカス移動を整える。
- 主要操作をキーボードだけで完了できるようにする。
- 文字サイズ拡大や OS の文字設定でレイアウトを壊さない。
- 色だけで状態、エラー、必須項目を伝えない。
- prefers-reduced-motion に配慮する。
- オフライン、同期中、送信失敗、更新待ちを視覚だけでなくテキストでも伝える。

## 確定前に確認する

- HTTPS で配信しているか。ローカル開発は localhost。
- 全主要ページから link rel="manifest" を辿れるか。
- id、start_url、scope を明示したか。start_url に個人識別子やトークンが入っていないか。
- 192、512、maskable のアイコンを実機で見たか。
- theme_color、background_color、アプリの初期背景が整合しているか。起動時にフラッシュしないか。
- HTML、JS/CSS、画像、API のキャッシュ戦略を別々に定義したか。
- ログアウトと権限変更のときに機密キャッシュをどう扱うか決めたか。
- 新バージョン検出、更新提示、再読み込みのフローがあるか。
- 送信操作に冪等性、再試行、同期状態の表示があるか。
- 未送信フォームと編集中データが更新や再起動で失われないか。
- オフライン画面が自サービスの文脈を持っているか。
- 機内モード、低速回線、アプリ再起動、新バージョン公開をまたいで重要タスクを完遂できるか。
- iOS Safari、Android Chrome、デスクトップ、未インストール状態を通したか。
- キーボードとスクリーンリーダーで主要操作ができるか。

## 運用開始後に見る

- Service Worker の更新失敗、キャッシュエラー、同期失敗。
- インストール率ではなく、インストール後の継続利用率と重要タスク完了率。
- 通知許可率ではなく、通知経由の完了率と解除率。
- オフラインで何ができなかったかを記録し、対象を広げる。
- 初回アクセスの表示速度、インストール済み起動時の表示速度、低速回線で操作可能になるまでの時間、キャッシュ命中時と未命中時の挙動。
